# Стенд GREEN-API

Демо-стенд тестового задания: чат-клиент Telegram на GREEN-API. По умолчанию
работает на подменённом бэкенде — посетителю не нужны ключи инстанса. Заглушка
`mock-green-api.js` оборачивает `window.fetch` и отвечает на методы GREEN-API
(`getStateInstance`, `checkAccount`, `sendMessage`, длинный поллинг
`receiveNotification` и остальные) заранее подготовленными данными, включая
автоответ собеседника.

## Два режима

| Режим | Как включить | Кто отвечает |
| --- | --- | --- |
| Демо (по умолчанию) | открыть стенд | заглушка |
| Свой инстанс | «Выйти» в меню → войти со своими `idInstance` и `apiTokenInstance` | настоящий GREEN-API |

Заглушка перехватывает запрос **только** если в адресе стоит демо-инстанс
(`/waInstance4100000001/<метод>/demo-token`). Ключи посетителя не совпадают с
демо-парой, поэтому запрос уходит в сеть как есть — вход проверяется настоящим
API, и ошибки приходят настоящие. У GREEN-API открыт CORS
(`Access-Control-Allow-Origin: *`, preflight отвечает 200), поэтому браузерный
клиент с чужого домена, включая GitHub Pages, работает без прокси.

Демо-ключи подставляются в `localStorage` один раз — при первом заходе и только
если там пусто (флаг `green-api-stand:seeded`). После выхода и входа со своими
ключами перезагрузка страницы не возвращает посетителя в демо-режим.

Что лежит в этом каталоге:

- `mock-green-api.js` — исходник заглушки. Это единственный файл стенда,
  который правится руками; сборщик копирует его в `public/` приложения и
  подключает перед бандлом.

## Откуда берётся исходник

Само приложение живёт в отдельном локальном репозитории `green-api`
(каталог `apps/telegram`, React 18 + Vite). По умолчанию сборщик ищет его в
`../green-api` относительно корня этого репозитория, то есть в соседнем
каталоге. Другой путь задаётся аргументом `--src` или переменной окружения
`GREEN_API_SRC`.

Исходный репозиторий только читается: всё копируется во временный каталог
(`fs.mkdtemp` в системном `tmp`), там ставятся зависимости и выполняется
`npx vite build --base=./`. Флаг `--base=./` (без правки `vite.config.ts`) даёт
относительные пути к ассетам — это нужно, потому что стенд публикуется в
подкаталоге сайта.

## Как пересобрать

```bash
# из корня репозитория портфолио
GREEN_API_SRC=/path/to/green-api npm run stand:green-api

# или явным аргументом
node scripts/build-stand.mjs --src /path/to/green-api
```

Скрипт: копирует исходники во временный каталог → `npm install` → `vite build`
→ вставляет `<script src="./mock-green-api.js"></script>` перед первым
module-скриптом → очищает приёмник и кладёт туда содержимое `dist/` → проверяет
результат и печатает сводку. Временный каталог удаляется в любом случае.

Дополнительные флаги (для отладки):

- `--out <путь>` — приёмник, по умолчанию `public/demos/green-api`;
- `--keep-temp` — не удалять временный каталог;
- `--skip-install` — не запускать `npm install`.

## Требования

- Node 22+.
- Сеть: `npm install` тянет зависимости приложения из npm.

## Результат и коммит

`public/demos/green-api/` — **сгенерированный артефакт**. Руками его не правят:
после пересборки каталог целиком перезаписывается. Имена хешированных ассетов
могут меняться от сборки к сборке — это нормально.

Артефакт нужно **коммитить**: сайт публикуется на GitHub Pages как статика, и
другого способа получить стенд на проде нет.

## CI

CI стенд **не пересобирает**: workflow деплоя собирает только сам сайт
(`npm ci && npm run build`), а исходного репозитория `green-api` в CI нет.
Поэтому обновлённый стенд коммитится вручную после локальной пересборки.
